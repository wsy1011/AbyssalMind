# Abyssal Mind Research Brief 工作流

本流程适用于以一篇论文为核心、服务交通、能源、航运等领域研究者和从业者的中文图文解读。目标不是复述摘要，而是把论文的证据、政策含义、经济约束和工程条件放到同一篇可核查的文章里。

## 1. 接收与建档

当你提供一篇 PDF 或 Zotero 条目时，我会先建立文章 `slug`，并确认：

- 原文标题、DOI、期刊、发表日期和 APA 引用；
- 全部作者、参与机构、共同第一作者及其单位、通讯作者及其单位；
- PDF 是否完整，补充材料、数据仓库和许可信息是否可取得；
- 拟服务的问题，例如政策评估、技术路线、成本、运营或基础设施。

原始 PDF、全文导出和笔记保存在 `.local/research-briefs/<slug>/`，不进入公开仓库。公开页面只放可发布的正文、经许可使用的图像和必要的引用。

## 2. 建立证据卡

我会通读论文正文、图表和补充材料，形成一份内部证据卡。它至少记录：

- 研究问题、研究对象、空间与时间范围；
- 方法、数据来源、功能单位、情景设定和比较基准；
- 可直接陈述的主要发现及其对应页码、图号或表号；
- 作者已说明的假设、局限性和未覆盖的问题；
- 与文章主题直接相关的政策、经济和工程信息。

文中每个具体数字、年份、情景结论和作者归因都必须回到原文核对。论文没有回答的问题，会明确标为 Abyssal Mind 的解释，或不写入正文。

## 3. 提取并筛选论文图像

优先使用 Zotero PDF Figure 插件提取图像。每张拟采用的图都按以下要求处理：

1. 从 PDF Figure 的结果中选取完整图版，保留全部面板、坐标、图例、单位和必要的图内说明；不重绘、不裁切数据面板、不改动图中数据。
2. 只选对论证有作用的图。通常保留 2—5 张：一张概览或机制图，加上支撑政策、成本或工程讨论的关键图。
3. 在页面中将图放在对应论述之后，并写简洁中文图解：先说明图展示的对象与口径，再说明读者应该如何理解，不把图注逐字翻译成正文。
4. 图像发布前核对论文许可或获得使用授权；若不能公开使用原图，则改用文字解读或另行制作注明来源的原创示意图。

每张进入正文的图都必须逐图解读，不能将多张图合并成一段笼统说明。每图都要有自己的问题、指标与口径、主要比较结果、对政策、经济或工程判断的含义，以及该图不能支持的推论。图前说明它要回答的问题，图后紧接 1—2 段解读；若没有可写的解读，该图不进入文章。

提取后必须做一次图版完整性核验：将提取图与 PDF 原页逐一对照，检查面板编号、坐标轴、图例、单位、注释和边缘元素是否齐全；再在网页中以原始比例预览，确认没有因 `object-fit`、裁切或缩放而遮挡信息。只有通过这两项检查的图片才能进入公开页面。核验结果记录在 `provenance.json`。

## 3.1 图版与论证覆盖清单

在写正文前，先筛选最能支撑文章主线的关键图，并记录“采用 / 不采用”的简短理由。通常采用 2—5 张，数量由论证需要决定；不追求覆盖全部主文图表。每一张入选图必须绑定一个正文小节和一条中心判断。发布前检查入选图的网页图号、图片与逐图解读是否一一对应。

提取记录、原图页码、插件结果 ID 和 SHA-256 校验值保存在 `assets/articles/<slug>/provenance.json`，供项目内部追溯，不出现在公开文章页面。

## 4. 写作结构

每篇 Brief 使用同一套读者可预期、但可按论文调整的结构：

1. **标题与元信息**：中文标题，后接期刊名；标题下方放主题 hashtag。引用框只保留这篇论文的 APA 格式引用。
2. **开篇导语**：先介绍研究团队、共同第一作者和通讯作者及其单位，再用一段话说明研究做了什么、为什么值得读。
3. **结论先行**：用 3—5 条短结论说明论文真正支持的判断。
4. **研究问题与证据**：交代对象、方法、情景、数据和证据边界。
5. **主体讨论**：围绕论文实际内容展开政策、经济、工程或运营讨论；图像嵌入相应段落，而非集中堆放在文末。
6. **启示**：面向船东、港口、燃料供应商、研究者或政策制定者，提出与证据相称的行动含义。
7. **局限性**：说明论文模型、数据、范围或外推上的限制。
8. **原文与数据**：放 DOI、开放数据入口及图像授权信息。

文章会避免把“启示”写成项目筛选清单，也不展示资产路径、提取步骤、哈希值或其他生产过程信息。

## 4.1 深度门槛：避免“短评化”

Research Brief 不是摘要改写，也不是图片集。除标题、引文和图注外，正文默认不少于 1,800 个中文字符；篇幅应由论文的证据量决定，而不是机械凑字数。每个核心小节至少完成一个完整论证链：**论文结果 → 证据或图表 → 成立条件 → 对具体主体的含义 → 边界**。

- **启示**至少分别讨论两个相关主体，例如船东、港口/燃料供应商、政策制定者或研究者；每一项要说明该做什么、依据哪项结果、何种条件下不成立。
- **局限性**逐项说明受影响的结论、论文中受限的假设或数据、这会如何改变解释，以及需要什么数据或测试来收窄不确定性。
- **政策、经济与工程**只要论文涉及，就不能各用一句带过；至少各形成一段有证据支撑的讨论。若论文不涉及某一维度，应明确省略原因。
- 每段完成后做“删段测试”：删去该段会不会损失证据、条件或可行动含义？若会，保留并写实；若不会，合并或删除。

## 5. 编辑与事实复核

初稿完成后必须依次进行两轮编辑：

1. **专业编辑**：先使用 `nature-polishing`，按 Nature 风格的证据约束检查论证。重点是压缩重复内容，分清“作者发现”和“编辑部解读”，让政策、经济与工程讨论都能回到论文证据或明确的外部一手来源。
2. **中文可读性编辑**：再使用 `humanizer-zh` 清理模板化表达、空泛强调、模糊归因和不必要的排比，使语言自然、克制、具体；不得改变已核对的事实、数字、单位、引用和证据边界。

最后逐项复核作者与机构、APA 引用、DOI、图号与页码、数量与单位、链接、许可信息和中文表述是否超出原文支持范围。

## 6. 入库、构建与发布

完成后的内容放入以下位置：

```text
content/articles/<slug>.md                 正文源文件
content/articles.json                      首页卡片与内容索引
assets/articles/<slug>/figure-*.png        已核准的论文图像
assets/articles/<slug>/provenance.json      内部图像溯源记录
articles/<slug>.html                       构建后的公开文章页
```

发布前会执行构建脚本，检查 Markdown 到 HTML 的渲染、所有图片路径、首页卡片链接和移动端排版。只有通过这些检查后，才提交并推送至 GitHub Pages。

## 7. 你提供 PDF 后，我会先交付什么

我会先给出一份简短的选题确认单：论文元数据、作者与机构、建议标题、拟采用图表、文章切入点和可能的证据边界。确认无误后再完成全文和页面。若你已经说明“直接做”，则从建档、写作到发布连续完成。
